# VCoin — Universal Earning Scale (v1)

A real, unified formula for "bigger action = more VCoin," applied
consistently across all apps — same logic real loyalty systems use:
airline miles (distance), credit card cashback (dollars spent), hotel
points (nights stayed), Strava's distance-based fitness scoring.

Core principle: one base VCoin-per-unit-of-real-value rate, applied to
each app's natural unit:
- VOID (rides/delivery): miles traveled + minutes
- HVNTZ (hunts): checkpoints completed, difficulty tier
- Vavlt Stvdios: stream duration + real viewer engagement
- VDP (business activity): real revenue generated, reputation tier
- VXLLAGE: real engagement received, not just posting
- CVNVO: verified safety check-ins, completed dates
- CHOPZ/VENVS: real transaction value

Critical constraint: per the Mistplay model already established,
VCoin payouts should scale with real, external revenue generated by
that action — not an arbitrary invented point value. This keeps the
scale sustainable rather than growing faster than real revenue
supports.

Anti-exploitation safeguard: real loyalty programs use diminishing
returns or daily/session caps to prevent gaming the system. Recommend:
full rate up to a reasonable daily threshold per app, tapering after —
same principle as credit card category spending caps.

```
VCoinEarningEvent {
  id, userId, sourceApp: string
  actionType: string
  measuredUnit: number
  baseRate: number
  dailyCapApplied: boolean
  realRevenueSource: string
}
```

Fit with existing systems: natural extension of the shared progression/
tiering engine already identified in the Ecosystem-Wide Shared Systems
Review — formalized as VCoin's actual earning formula.

## Implementation status (added when this file was placed into the repo)

**Not built, and the gap it describes is real and currently
load-bearing across eighteen apps.** Verified directly rather than
assumed: searching every non-vendor `.js` file in the repo for
`awardVCoin`, `grantVCoin`, `mintVCoin`, `earnRate`, `EARN_RATE`,
`VCOIN_PER_*`, and `VCOIN_REWARD` returns **zero matches**. There is no
earning engine, no rate table, no `VCoinEarningEvent`, and no cap
logic anywhere.

**How VCoin is actually awarded today.** There is no minting operation
at all. `v3/lib/vcoin.js` exposes exactly one way to move value —
`transfer(fromUserId, toUserId, amount)` — so every app that wants to
reward a user does so by transferring from its own platform account
over `POST /api/vcoin/transfer`. Eighteen apps do this: CHOPZ, CVNVO,
DREAMS, HVNTZ, VACAY, VAGO, Vavlt Stvdios, VDP, VENVS, VEX, VOID, VOID
MAGIC, VOKEN, Vvltvre Flix, Vvltvre Music, Vvltvre Pods, Vvltvre
Studios, and VXLLAGE.

**Which means the problem is sharper than "no formula exists."** Each
of those eighteen apps independently decides its own amounts, at its
own call sites, with no shared rate, no shared unit, and no shared
name. There is no single place to look up what an action is worth, and
no mechanism that would notice if two apps priced comparable actions
an order of magnitude apart. The document's framing — a missing
*formula* — understates it; what is missing is the **vocabulary**. An
earning scale cannot be applied to a system whose only primitive is an
untyped transfer of an arbitrary number.

**The one existing counter-example, and why it is instructive.**
`cvnvo/lib/blindDate.js` defines `DATE_TOKEN_PRICE_VCOIN = 20` as a
real named constant sourced from its own spec doc. That is a *price*,
not an earning rate, but it shows the pattern this document needs:
named, documented, traceable to a source, rather than a literal buried
in a call site.

**Two real design problems this document has not yet solved**, worth
recording before anyone implements it:

*First, `realRevenueSource` is a string in a struct, which will not
enforce anything.* The Mistplay constraint — payouts scale with real
external revenue — is the most important idea in the document and the
easiest to quietly violate. A free-text field naming a revenue source
does not verify that revenue exists or that the payout is a sane
fraction of it. Making that constraint real means the earning call
needs an actual revenue amount to divide into, not a label. The
ecosystem already has the shape for this: `hvntz/lib/revenueStack.js`
computes real splits against real amounts earned. The earning scale
should take the same posture — compute from a number, not annotate
with a name.

*Second, the daily cap has to live somewhere that can see across
apps.* "Full rate up to a daily threshold per app, tapering after"
is exactly right as policy, but per-app caps enforced per-app are
trivially defeated by spreading activity across apps — which is
precisely what a user optimizing for VCoin would do in an ecosystem
this large. The cap belongs in V3, where every earning event
necessarily passes through, not in eighteen separate call sites.
That also implies a new route: earning cannot stay a bare `transfer`
if it needs to be rate-limited by policy.

**Where this would go.** V3, alongside `lib/vcoin.js` — it is a ledger
concern, not an app concern, for exactly the cap reason above. It also
sits directly downstream of two open V3 items: an earning route is a
mutating money route, so it inherits the missing idempotency
(`V3_FIRST_PROMPT.md` task 3) and the missing transactional atomicity
that Postgres would provide (task 2). Building the earning scale
before those exist would mean building a third money route with the
same two known defects. Sequence accordingly.

**Not started, not blocked** — this is genuinely buildable work, just
work that is cheaper and safer after Postgres and idempotency land.
